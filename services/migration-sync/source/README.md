# Places outbox capture adapter

This opt-in pilot captures favorites and likes/dislikes for an immutable list of Genesis place UUIDs. Install only with the explicit operator command after reviewing the source DDL and role grants. It is not automatically installed when the worker starts. The target catalogue must already contain the same local place IDs. Shop, treasury and credits are excluded.

`places_outbox_v2` is a transactional outbox, not logical WAL decoding. Its monotonically committed transaction ordinals use the envelope's hexadecimal cursor representation; they must never be compared to PostgreSQL WAL LSNs. Source generation and adapter identity fence distinct capture histories. A restored/replaced source must receive a new reviewed generation and baseline before capture resumes; restoring the same generation and reusing positions cannot be treated as a safe failover.

A source-local BEFORE STATEMENT trigger serializes favorite and like mutations under the same lock with a transaction advisory lock. Relevant rows and accepted command receipts share a transactional counter and commit atomically. Rollbacks consume no committed position. Internal SQL writes and deletes are captured even when they bypass HTTP. TRUNCATE is rejected because it cannot preserve this snapshot/capture contract. Disabling triggers, replacing the table, changing the capture schema, or bypassing triggers invalidates the pilot and requires stopping capture and a reviewed baseline.

Bootstrap takes that same source lock only while establishing a repeatable-read snapshot and its capture boundary, then releases it before exporting rows or contacting the target. The source pool needs at least two connections. It refuses an occupied destination scope and unsupported rows. Baseline export is bounded to 100,000 combined favorite/like rows; transactions over the envelope limit stop capture instead of being truncated.

The installer needs DDL privileges on `public.user_favorites` and `public.user_likes`, and permission to create `migration_capture`. All functions run as the caller, not SECURITY DEFINER. The application role needs schema usage, function execution, SELECT on control/scope/transactions/receipts, UPDATE on control/transactions, INSERT on transactions/changes/receipts, and usage on the changes identity sequence, in addition to its existing business-table permissions. Review explicit grants for the actual deployment roles; the installer does not guess role names or grant public access.

The runtime source account needs only CONNECT, schema usage, and SELECT on capture tables and the source favorite/like/catalogue tables. It makes no source business writes and performs no source acknowledgements. Source history and receipts are retained; no automatic retention/pruning is implemented. Target capture progress advances only after the full envelope is durably stored. A crash between enqueue and progress update safely repeats the immutable envelope.

The serialization lock adds contention to all source favorite and like writes, including writes outside the scope. Rehearse latency and source storage growth before enabling it. This adapter is a bounded fallback for environments where logical CDC prerequisites are not established; it is not evidence that production capacity, privileges, retention, or failover have been verified.

Version 2 adds `user_likes` capture, including the boolean vote, activity, creation time and update time. A like-to-dislike update is a replacement fact; deletion removes the fact. Both tables share a transaction cursor, so a source transaction touching both becomes one atomic target application. Target counts are rebuilt from those facts; source cached counts are not copied.

Installation and polling reject version 1 sources instead of silently claiming like coverage. Existing version 1 streams remain historical metadata only for this adapter; stop them and prepare a reviewed version 2 source installation/new clean destination baseline. The installer does not alter an existing source capture history, reset generations, or silently upgrade triggers. Apply the destination schema migration that permits the version 2 adapter before bootstrapping. Existing target favorites **or likes** in the selected scope reject bootstrap, preventing a mixed-time baseline.

No client operation header, gateway dual routing or source application change is required for source-only interaction synchronization. Optional favorite command receipts remain supported; likes have no native duplicate command lane. A transaction that mixes a receipt-bearing favorite command with like changes is rejected by the classifier rather than silently dropping its extra effects.
