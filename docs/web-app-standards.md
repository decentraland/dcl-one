# Web app architecture standards

Normative standards for UI state, data fetching and project structure in this repository. Each section records a decision that has been made; areas without a decision say so instead of guessing. Styling and components are in [UI standards](ui-standards.md), tests in [Frontend testing standards](frontend-testing.md), and the decisions behind this document in the [web app server state ADR](adr/2026-11-04-web-app-server-state.md).

Each rule is marked by how it relates to the code today: **current** describes what the apps already do, **required** is the rule for new and migrated code where the code does not yet follow it.

The apps named in the table below are evidence of current practice, not an allowlist. Pages, routes and data wiring always live in the app that owns the route ([App-specific UI](ui-standards.md#app-specific-ui)). `apps/ui3` is not a destination: no new or migrated code goes there, and its UI is moving to `library/ui`.
- Exception: the Explorer HUD's two hosts share their data wiring (page-engine protocol, drivers, sign-in and server reads) in `library/explorer-core`, beside the HUD UI in `library/ui/apps/hud` ([ADR](adr/2026-11-10-shared-explorer-hud-ui.md)); each host keeps only its own wiring.

Moving code out of it to `library/ui` or to the app that owns the route is allowed. An urgent fix to existing code in a frozen area is allowed as the smallest in-place change with a test that covers it, when the pull request states why it cannot wait for the migration and `@decentraland/web-applications` (CODEOWNERS for `/apps/ui3/`) approves it.

Importing a module from another app (for example through `@ui/*`) does not make it that app's code: UI shared across apps or with the Explorer HUD follows the shared-UI rule in the UI standards. Migration responsibility stays with the owning teams.

## Server state

**Decision:** TanStack Query is the only cache for server state that UI code reads. Do not add another cache, store or module-level map for it. A custom cache that exists today is an [exception](#exceptions-and-migration-gates).

### QueryClient

- **One client per host, provided by the host.** The host is the entry point of each app that renders the pages: the root route of a server-rendered app, or the component that renders the router of a client-only app. A page or component does not create a client of its own. Current hosts: the `apps/sites` root (`apps/sites/src/routes/root.tsx`), and the native Shop mount, which has no provider (see [exceptions](#exceptions-and-migration-gates)).
- **Lifetimes (required):**
  - Browser client: one per page lifetime, created with `useState` in the host component. In an app that renders on the server, also: render client, one per server request, created the same way; loader client, one per loader call (see [Server rendering](#server-rendering-and-navigation)).
  - No module-level `QueryClient`, on the server or in the browser. The Shop fallback in `apps/ui3/src/shop/market/components/kit.tsx` (`fallbackClient`) is one today; see the [exceptions](#exceptions-and-migration-gates).
- **Defaults.** Reference values, taken from the current `apps/sites` root: `{ queries: { retry: false, staleTime: 30_000 } }` (`apps/sites/src/routes/root.tsx`). A host adopts these defaults unless it records a reason to differ. Per-query `staleTime` that differs by data type is declared in the key and options factory (current: `STALE` in `apps/ui3/src/data/queryKeys.ts`). This document does not set other values.
- **Current gaps.** Shop code also creates fallback clients with other defaults: a client per mount in `apps/ui3/src/shop/checkout/services.tsx` and a module-level one in `apps/ui3/src/shop/market/components/kit.tsx`. `apps/ui3/src/shop/checkout/demo.tsx` creates a client per mount for its demo harness, not as a fallback for a host without a provider. The native Shop mount (`apps/sites/src/routes/shop/native.client.tsx`) renders without a provider. The Explorer HUD's in-world Shop creates a client of its own, scoped to the Shop page (`rendering/bevy-explorer/source/react-web/src/features/shop/ShopQueries.tsx`). They are listed in [Exceptions and migration gates](#exceptions-and-migration-gates).

### Query keys and options

- **Required:** one key and options factory per data domain, used by both the loader and the components that read the data. It returns the key, the `queryFn` and the `staleTime`, so a loader cannot dehydrate a key that a component then reads differently.
- **Every input that changes the response is part of the key:** route parameters, filters, sort, locale, chain, endpoint or realm, and the account address for account-scoped data. A key that omits one of them shares one cache entry between different responses.
- **Pagination.** A `useQuery` that requests one page at a time puts the page (or cursor) in its key, so each page is its own entry. A `useInfiniteQuery` keeps all pages and page parameters under one stable key for the dataset (filters and sort, not the page) and passes the cursor or offset as `pageParam`. Do not put the changing page in an infinite query's key: it splits the list into separate entries.
- **Key shape (required for new keys and for keys a migration touches):** public data is `[domain, ...inputs]`; private data is `["private", account, domain, ...inputs]`. The first segment of a public key names the domain and is stable. For keys in the new shape, sign-out removes the prefix `["private"]` and an account switch removes `["private", previousAccount]`, with no predicate needed; account-scoped keys not yet migrated need a `predicate` or `queryClient.clear()` (see [Sign-out and account changes](#sign-out-and-account-changes)). Existing keys such as `qk.profile` are not rewritten by this standard.
- **Current:** `apps/ui3/src/data/queryKeys.ts` (`qk`) is a factory for part of the data. Other keys are literals at the call site, including `["saved-by", itemKey]` (`apps/ui3/src/shop/market/components/SavedBy.tsx`), and invalidations name keys as literals too (`apps/ui3/src/shop/checkout/lib/after-purchase.ts`). Move literals into a factory when the code is next changed.
- Read data in a hook named for what it returns; the hook calls the factory and `useQuery`. Pass the `signal` from the query function context to `fetch` so an unmounted query aborts. Current: `useProfile` (`apps/ui3/src/data/hooks/useProfile.ts`) uses only the key factory `qk.profile`; its `queryFn` and `staleTime` are inline and repeated in `prefetchPassport`, so it is not the full key and options factory this section requires for new code.
- Use `enabled` for queries that wait on an input. Use `select` only to derive a view for one component: it does not change what the cache stores. Map a response into its final shape inside the `queryFn` (or the fetcher it calls) when other code reads or writes that cache entry.

### Where code lives

**Required** for new code. Data wiring (fetchers and domain logic, key and options factories, query hooks, route loaders) belongs to the app that owns the route, under `apps/<app>`, apart from the components. The Explorer HUD is the exception: its two hosts share their data wiring in `library/explorer-core` (see [Scope](#scope-and-relation-to-the-contributor-guides)). Components follow the [UI standards](ui-standards.md): shared components go to `library/ui` once it is implemented and adopted by the app, and until then new app-specific UI stays in the owning app. No folder layout is decided for other apps; only the Sites layout is:

| Kind | `apps/sites` |
| --- | --- |
| Fetchers and domain logic | `src/data/lib/<domain>/` |
| Key and options factories | `src/data/lib/<domain>/` |
| Query hooks | `src/features/<domain>/` |
| Route loaders and head | `src/routes/` |

Sites layers are `core`, `data`, `features` and `routes`, and a layer imports only the layers `apps/sites/src/boundaries.json` lists for it; `apps/sites/scripts/boundaries.test.ts` enforces this. No decision yet on enforcing layers in other apps.

Current practice, as evidence only: `apps/sites` has no query hooks or key factories.

### Mutations and invalidation

- Use `useMutation` where the interface needs the pending or error state of the call (current example: `apps/ui3/src/social/SocialPage.tsx`). A call made from an event handler may instead await the request and then invalidate.
- After a write, invalidate or update every query the write changes, through the key factory. Group the invalidations of one domain event in one helper (current: `invalidateAfterPurchase` in `apps/ui3/src/shop/checkout/lib/after-purchase.ts`). A mutation that leaves the cache stale is a defect.
- Update the cache by hand (`setQueryData`) only when the response of the write carries the new data. If an update is applied before the response (an optimistic update), roll it back on error with the previous value returned from `onMutate`. No code under `apps/` or `rendering/bevy-explorer/source/react-web` uses `onMutate` on `origin/main`, so this describes a rule for new code, not a current practice.

### Sign-out and account changes

- **Required:** on sign-out, remove every private entry from the cache. Either call `queryClient.clear()` (complete, and the default while old-shape keys exist), or remove both shapes: the prefix `["private"]` for keys in the new shape, and a `predicate` matching every account-scoped key not yet migrated (the examples listed under the account switch rule below). Removal is not invalidation: invalidated data is still readable until it refetches. At the time of writing, the only code that does is the Explorer HUD's Shop-scoped client (`rendering/bevy-explorer/source/react-web/src/features/shop/ShopQueries.tsx`): another account or a sign-out remounts the Shop with a fresh client, and the replaced one is cleared after that commit. Elsewhere only test code calls `clear()` on a client.
- **Required:** on an account switch, remove every private entry of the previous account. Either call `queryClient.clear()` (complete, and the default while old-shape keys exist), or remove both shapes: the prefix `["private", previousAccount]` for keys in the new shape, and a `predicate` matching the previous account's segment for account-scoped keys not yet migrated (current examples: `qk.friends` and `qk.notifications` in `apps/ui3/src/data/queryKeys.ts`, the `["chat-conversations", kind, identity.address]` key in `apps/ui3/src/explorer/frames/ConversationChat.tsx`, and the Shop purchases keys `[SHOP_QUERY_KEYS.purchases, account, ...]` in `apps/ui3/src/shop/history/ActivityPage.tsx` and `apps/ui3/src/shop/history/BuyStatusPage.tsx`). Adding account-switch handling to a domain counts as a migration that touches its keys, so they move to the new shape. Invalidation alone is not enough, because the previous account's data stays readable in memory on a shared device.
- **Required order on account switch and sign-out:** the account in context changes first, so mounted components move to their new keys; then `await queryClient.cancelQueries(...)` on the entries being removed; then `removeQueries` (or `clear()`). Alternatively, gate cache writes by the current account. Removing before the context changes lets mounted observers recreate the old entries. "Changes first" means the old-account observers have stopped using the old keys (the switch has rendered), not that a state update is queued; the account-switch validation case asserts that no old entry reappears after removal.

## Server rendering and navigation

The contract for routes whose loader hands server data to TanStack Query hooks. No code under `apps/` or `rendering/bevy-explorer/source/react-web` does this on `origin/main` today: Shop routes prime the custom Shop cache instead (`apps/sites/src/routes/shop/page.tsx`).

These rules apply to apps that render on the server. A client-only app has no loader handoff: its components fetch with the browser client, and required data follows [Required data on client navigation](#server-rendering-and-navigation) on every navigation, including the first.

- **Loader.** The loader creates its own `QueryClient`, loads the route's data with the key factory, awaits every query it will dehydrate, dehydrates only settled successful queries (no pending or streamed queries), discards the client, and returns the dehydrated state. The page renders under `HydrationBoundary`.
- **Required and optional data.** Required data uses `fetchQuery` or `fetchInfiniteQuery`. On a document request the loader catches the typed error (not found, unavailable) and sets the HTTP status itself: it throws `data(null, { status })` or a `Response`, which the route `ErrorBoundary` renders (it reads the response with `isRouteErrorResponse`), or it returns status-bearing loader data that the page renders. The `ErrorBoundary` does not set the status, and a typed error that escapes the loader becomes a 500; a failure never ends on a loading page. Current examples: `docs.$.tsx` (`apps/sites/src/routes/routes/docs.$.tsx`) throws `data(null, { status: 404 })` and the root `ErrorBoundary` uses `isRouteErrorResponse` (`apps/sites/src/routes/root.tsx`); `shopLoader` returns status-bearing data through `session.wrap(..., { status })` (`apps/sites/src/routes/shop/loader.server.ts`) and the page renders it. Optional data uses `prefetchQuery` or `prefetchInfiniteQuery`: a failure means the browser fetches it. For client navigations see Navigation.
- **Navigation.** The route exports a `clientLoader` that does not call `serverLoader`, returns `null` (never `undefined`), does not set `clientLoader.hydrate`, and the page passes `loaderData?.dehydratedState` to `HydrationBoundary` (after a client navigation `loaderData` is `null`, so that expression is `undefined` and nothing is hydrated). Current: `shopClientLoader` in `apps/sites/src/routes/shop/page.tsx` returns `null`. Dehydrated state reaches the browser only with the first document, into an empty cache. After that, the route's components fetch on the browser client through TanStack hooks. The route's own server loader is not re-run on client navigations; freshness comes from `staleTime` and key invalidation. The root loader is separate and follows its own `shouldRevalidate` (`apps/sites/src/routes/root.tsx`): after any form or fetcher submission (including GET forms) it uses React Router's default, it always revalidates while the Creator Hub framed by the Explorer reloads for another account, it never revalidates on a navigation to the same pathname, and otherwise it uses React Router's default. Do not assume the root loader runs again on every client navigation.
- **Required data on client navigation.** There is no HTTP response, so no status code. The component reads required data with the same query options and uses the function form of `throwOnError`, so only an initial load reaches the boundary: `throwOnError: (error, query) => query.state.data === undefined && isRouteFatal(error)`, where `isRouteFatal` is true for the errors that mean the route cannot render (not found, unavailable). The failure then reaches the same route `ErrorBoundary` and renders the same not-found or unavailable UI as the document request. A background refetch error with data already shown keeps the data and shows the error inline. A loading state while the query runs is allowed; ending on an empty or permanent loading page is not. The fetcher throws typed errors (for example a not-found error carrying 404): the loader converts them to a status-bearing response on a document request, and the component's `throwOnError` hands them to the boundary on a navigation. The `ErrorBoundary` recognizes both a route error response (document request) and the typed client error (navigation). Recovery resets or removes the errored query itself, targeting the route's required entries through the key factory (exact keys where appropriate), in two separate paths. Retry: the route `ErrorBoundary` resets or removes those entries and then clears React Router's error state (`useRevalidator().revalidate()` or a navigation). Leaving: when the boundary unmounts because the user navigated away, it only resets or removes those entries and starts no navigation or revalidation; the navigation in progress already clears the router error, and returning later makes a fresh request. Queries that succeeded or hold background data are not affected. A `QueryErrorResetBoundary` `reset()` alone only sets a shared flag that the next mounting query under that boundary consumes; it is reliable for an immediate Retry that remounts the failed query, not as a leave-and-return guarantee.
- **Browser-reachable data.** The factory's `queryFn` must be callable from the browser: a public API, or a resource route in the owning app. A route whose data the browser cannot fetch (server-held credentials, private upstream) records an exception in the [exceptions table](#exceptions-and-migration-gates).
- **Nested loaders.** Each route loader dehydrates only its own queries, under its own `HydrationBoundary`. A child never re-sends a parent's queries.
- **Payload.** Dehydrate only the queries the route needs and that are safe for the browser. Cap a prefetched infinite query to its first page. Measure the dehydrated bytes per route; this document sets no size threshold until they are measured.
- **Request isolation.** Request-scoped data is never held in module state; see [Server module state](#server-module-state).

## Client state

State is client state when the server does not own it: view preferences, filters, open dialogs, drafts, a signed-in identity held in the browser. Client state never becomes a second copy of server data; the one exception is a draft, below.

- **Decision:** the mechanism follows current practice. Use React state or context for state local to a component tree. Use a small external store read with `useSyncExternalStore` for state shared across the tree or read outside React (current example: `apps/ui3/src/shop/cart/store.ts`). Context is also used to inject services and session values (`ShopServices` in `apps/ui3/src/shop/checkout/services.tsx`).
- No dependency is added for client state. Choosing a state library is a new decision, not a local one.
- A store that holds account data is scoped to the account and does not leak it to the next one (current example: the cart store keeps one cart per account; `scopeTo` in `apps/ui3/src/shop/cart/store.ts` switches to the new account's cart and merges the anonymous lines on sign-in, and `apps/ui3/src/shop/wallet/context.tsx` calls it when the account changes).
- **Server snapshot, draft and client-owned data.** Data the server returns, including a collection the user will edit, is owned by the query cache; that is the server snapshot. Optimistic changes to server data are applied to the query cache with rollback (see [Mutations and invalidation](#mutations-and-invalidation)), not to client state. Unsaved edits are a draft in client state: the draft may be seeded from the snapshot when editing starts, records which snapshot it came from (for example its `dataUpdatedAt`), and is cleared after a successful save, which updates or invalidates the snapshot. A draft without unsaved edits re-seeds when the snapshot changes; a draft with unsaved edits is never silently overwritten. A save clears only the edits it submitted: edits made while it is in flight are kept, and the draft does not re-seed from the pre-save snapshot while the refetch runs. Data the server does not own at all (for example a cart kept in the browser before checkout) is client-owned and lives only in client state. No decision yet on a shared helper for drafts or client-owned collections.
- Build a store with a factory (current: `createCartStore` in `apps/ui3/src/shop/cart/store.ts`). The app may hold one browser instance at module level (current: `shopCart`), only for browser-only state that nothing request-derived writes during server rendering. On the server, a store is created per request or not at all; see [Server module state](#server-module-state). Tests create a fresh instance from the factory for each test. `apps/sites/src/features/components/auth/signin-store.ts` is a module-level browser store whose server snapshot is always `false`; it is cited as current practice, not as the factory pattern, and whether any server render path writes it is not inventoried here.

## Server module state

- **Required:** request-scoped data (identity, locale, anything derived from the incoming request) is never kept in module state. A module-level `Map` outlives a request and is shared by interleaved requests.
- Public memoization of upstream responses that do not vary by visitor is allowed (current: `ttlMemo` in `apps/sites/src/data/lib/ttl-memo.ts`, `publicFeedMemo` in `apps/sites/src/data/lib/public-feed.server.ts`). Key it by every input that changes the upstream response. State in a comment the configuration the memo depends on and that it is constant for the process; a key is sufficient only while that holds.
- Server memoization is not a substitute for the query cache: it is read by loaders, and the browser still reads through TanStack Query.

## Web3 and auth

Only rules backed by code are decided here.

- **Non-serializable objects stay out of cache state.** Providers, signers, host bridges, contract instances, sockets and abort controllers never enter dehydrated, persisted or query-cache state. They are passed through React context or dependency injection (current: `ShopWalletProvider`, which takes a `provider` getter from its host, in `apps/ui3/src/shop/wallet/context.tsx` and `ShopWalletHost` in `apps/ui3/src/shop/wallet/session.ts`).
- **Serializable data may live in query or client state:** the account address, the chain id, the status of a transaction.
- **Account in the key.** Account-scoped queries carry the account address in the key (see [Query keys](#query-keys-and-options)).
- **Where auth lives.** In the app that owns the route. Current practice: in Sites the auth module is `apps/sites/src/data/lib/auth`; identity and wallet code also exists in `apps/ui3/src/data/auth`.
- No decision yet on: transaction lifecycle state (pending, confirmed, failed), cache invalidation on network change or after on-chain confirmation, and event subscriptions for on-chain events.
