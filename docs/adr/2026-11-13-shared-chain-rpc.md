# ADR: Shared Ethereum RPC readers

- Status: Accepted
- Date: 2026-11-13

## Decision

The existing `catalyst-chain-index` crate owns Ethereum JSON-RPC log and header transport in its `rpc` module. LAND authorization and Shop consume that module directly. The client holds the outbound transport and endpoint; callers supply address and topic filters. It does not hold LAND registry settings.

The shared module owns response parsing, bounded log-range retries, header batches and generic transport, RPC and request-budget errors. LAND authorization retains registry filters, timestamp validity and batch retry policy, request accounting, cursor advancement, fold readiness and repair. Its error conversion retains domain error distinctions and messages. Shop retains receipt checks, index folds, reorganization handling and Credits settlement policy.

This keeps shared chain-reading mechanisms below domain policy without another crate, outbound client, pool or deployment. Existing layer dependencies already permit both consumers to use chain-index. No schema, HTTP route, authorization rule or request budget changes.

The Shop chain walk reads through the `logs` module's `LogSource`. A source answers the chain id it serves, the newest block, the newest finalized header, a header by height, a window of logs for a set of filter groups with the block it proved complete, and the block times of those logs. Each read reports the requests it took: for JSON-RPC, HTTP requests, a batch counting one, every request a window sends counted as it goes out (those that narrow its range and an address-count refusal after them included). A window also reports what the walk charges its log budget for it, which for `RpcSource` is its requests. That count is not a provider's bill and is not comparable across sources as is. `RpcSource` is the JSON-RPC implementation: one request per chain id, head, finalized or header read, and the window and block-time reads described above, including halving the address chunk when the endpoint refuses the count. The walk keeps the target block, confirmation depth, cursor, request budget, cancellation, reorganization handling and publication, and its backfill lanes read through the same source.

A portal that speaks the SQD portal protocol (the SQD portal, or chain-lake's) is read by the `portal` module's `PortalReader`, which is not itself a `LogSource`. It reads finalized blocks only (`/finalized-stream`), the dataset's latest and finalized heads, and the dataset's advertised first block where the portal publishes metadata. A page counts only when its body is complete and decoded and ends with the last block it covered; an empty answer, a cut body or a 204 covers nothing. The reader sends its key as `x-api-key` to the configured origin only, follows no redirect, and shares one rate limiter and cooldown per origin and key in the process. A portal's answer proves which blocks it covered, not that it holds every log of the addresses asked: the advertised first block bounds the dataset only, and address history is unknown unless the operator asserts it (`CHAIN_LOGS_PORTAL_ASSERT_FULL_HISTORY`), which is reported as an assertion.

With `CHAIN_LOGS_SOURCE=shadow` and `CHAIN_LOGS_PORTAL_URL`, each network runs a shadow worker. A walk alone and a shared walk call `LogSource::accepted` once a window's bracket and predecessor check pass, before its commit; the shadow takes the read only when its one slot is free and the read is within the hand-off bounds, otherwise it counts the skip, so the walk never waits and reads nothing more. The worker reads the same filters over the same blocks from the portal, with up to two drain rounds, within one 20-second deadline. It compares only a prefix anchored at the highest block where both sides hold a hash, and equal hashes there let that prefix be compared log by log; different hashes are a branch mismatch. A field one side lacks (a log's block hash, its time, its transaction hash) is not compared, and a read with such a field is incomplete, never equal. Only the dataset's advertised first block is cached (ten minutes); every comparable sample is anchored on its own. Backfill lanes are not compared. Outcomes are counted in `chain_logs_shadow_windows_total{net, result}`, `chain_logs_shadow_skipped_total{net, reason}`, `chain_logs_shadow_logs_total{net, kind}`, `chain_logs_shadow_unavailable_total{net, field}`, `chain_logs_shadow_blocks_total{net, kind}` and `chain_logs_portal_sends_total{net, kind}`. `CHAIN_LOGS_PORTAL_DATASET_{ETHEREUM,MATIC}` name the datasets (mainnet by default), `CHAIN_LOGS_PORTAL_API_KEY` (or its `_FILE`) the key, and `CHAIN_LOGS_PORTAL_MAX_RPS` (1) the rate. The walks commit RPC data in either mode.

With `CHAIN_LOGS_SOURCE=portal` and `CHAIN_LOGS_PORTAL_URL`, each network's walks read through `portal::admit::AdmittedPortal`, which wraps the RPC source. The chain id, the heads, every header (so the walk's bracket, checkpoints and rewinds) and the block times stay on the RPC; only a window's logs may come from chain-lake, and only when the chain id the walk read through the source is the dataset's: a projection whose RPC serves another chain reads everything from the RPC and leaves the portal's state alone. A window is admitted from chain-lake's coverage answer (`GET /datasets/<ds>/contracts`, read once per walk and again on a revision change), which must name the configured dataset and the network's chain: its finalized block `N` clamps the window, and an address is admitted when the answer lists it from a block at or below the window's first. An address that starts inside the window or is not listed is read from the RPC for the whole window. Before any portal log is accepted, the RPC's header at `N` must carry the answer's hash: the lake's durable history is then the walk's chain, which a page's own last header does not prove. Every page must be complete and name the answer's revision (`x-lake-coverage-revision`); two lines that give one block another hash or another time are a conflict; the portal side reaches the lowest last block of its pages, and each log is filtered again through the original filters, arity included. A page naming another revision drops every page read, and the window is admitted again from the original filters under a fresh answer, once. The addresses not admitted are then read from the RPC up to where the portal side reached, and the window ends at the lower of the two ends. Any other failure of the portal side (an unreadable or foreign answer, an anchor on another hash, a second revision change, a cut or conflicting page, a log the filters do not keep, the deadline) reads the whole window from the RPC; an RPC read that fails fails the window as in `rpc` mode. One deadline (`CHAIN_LOGS_PORTAL_DEADLINE_SECS`, 20) bounds the coverage read, the limiter's waits and every page; the portal side is a future of the walk, so a stop or a lost lease drops it. Three failed portal sides in a row, or an anchor on another hash, cool the network's portal for five minutes, during which windows go straight to the RPC; a hold the origin's limiter keeps (or kept, even with no window there to see it) cools it the same way until the hold passes, and every window that entered before that hold, a probe in flight included, settles nothing. Then one window probes it while the others keep to the RPC: only a probe that reads its pages ends the cooling, a probe dropped before it ends lets the next window probe, a window that read no page (uncovered, above the coverage, another chain) changes nothing, and a window that entered before the latest cooling began settles nothing. Each window settles one outcome, once its logs are known to merge: no position held twice, and every block both sides hold logs of given the same hash and time by both; otherwise the whole window is read from the RPC. A window charges the walk's log budget what its original filters cost as RPC log requests, and never less than the RPC log requests it sent, those of a split it discarded included, so a walk alone pauses where it does in `rpc` mode; it reports the RPC requests it sent and the portal requests apart, each RPC request counted as it is sent, so a read that fails or is dropped still counts in the send metrics. Backfill lanes carry the charge and the requests apart and also pay the header and block-time reads they send: logs from the portal carry their block's time, so a lane may read fewer headers and walk farther on the same budget than in `rpc` mode. Outcomes are counted in `chain_logs_portal_windows_total{net, result}`, logs by source in `chain_logs_portal_logs_total{net, source}`, RPC sends in `chain_logs_source_rpc_sends_total{net, kind}` and portal sends in `chain_logs_portal_sends_total{net, kind}`. An SQD portal publishes no coverage answer, so it admits nothing; `CHAIN_LOGS_PORTAL_ASSERT_FULL_HISTORY` stays a shadow and report label.

`catalyst shop compare-sources` compares one index over a block range: a read-only database connection for its filters, the walk's bracket on the RPC side, and the same filters on the portal. The network, the dataset and the RPC must name one chain before any window is read, or the run is refused. It reports the compared ranges, the uncovered ones with their reason (below the dataset's first block, above the RPC's safe head or the portal's finalized head, a window it could not anchor, or a read that failed, which ends the run with what was compared so far), the differences, the fields it could not compare, and the requests each side took. Every outcome prints its report: an unreachable database is reported before any chain read, and a failure by its stage, blocks and a stable kind, never by an upstream's text. It exits 4 when refused, else 1 when anything differed, else 3 when part of the range or a compared field was not compared, else 0; without a report, 2 is the argument parser's usage error and 1 a process setup error before the command runs (an invalid `NODE_POSTURE`); a difference always prints its report. The database's cursor of the index must be bound to the network's chain when it is bound at all (`database_chain` reports it).

## Validation

The chain reader parser tests run in chain-index. LAND integration tests exercise range hints, budget exhaustion, missing timestamps, batch fallback and retry, replay and publication. Shop tests exercise its filters, reorganization boundaries and Credits index consumers. A Shop integration test pins the order of the JSON-RPC requests the walk sends for one history, with each log request's block range and address count and each batch's headers: budgeted passes, an address-count refusal, missing timestamps, a pass with nothing new, a backfill lane and a reorganization rewind. The module dependency check enforces the existing layer graph. The portal client's tests run against a loopback portal: early ends, 204, cut bodies, size rejections, redirects and the key's header. The comparison tests cover the anchor, branch mismatches, conflicts and filter arity; the shadow tests cover the hand-off's bounds and a stalled portal; the pinned request traces are unchanged with a stalled shadow; and `compare-sources` runs over a fake chain and a fake portal serving it. The admission tests run a recording RPC source against a loopback lake: the durable anchor at the answer's finalized block rather than the page's last header, the anchor inside the deadline on a re-admission too, a revision change on a second batch that drops an address and lowers `N`, the window ending at the lower of both sides' ends, a persistent revision change, drift and arity, a stalled coverage read, a held limiter under concurrent walks, the cooling and its one probe (dropped, then succeeding), refused answers and the split charge. The admission tests also cover a walk on another chain (no coverage read, no anchor, the portal's state unchanged), one block given two times by two batches, a success older than a cooling, a window older than the latest cooling whose late success keeps the failures counted, a probe that reads no page, an origin hold ending in one probe among concurrent windows, an anchor held past the deadline counted in the window's requests, a duplicate that charges the split it discarded and settles once, a block the portal and the RPC give another time or another hash, a hold that passed unseen ending in one probe, an RPC window that narrows, is refused the address count and reads each address alone reporting the four requests the endpoint saw, a failed or dropped RPC read counting its requests in the send metric, and a hold set while a probe is in flight outliving that probe until one fresh probe follows it. In Shop, an nft walk with a portal covering every address pauses, backfills its late collection and writes the rows an RPC walk does, reports the RPC requests it sent and sends no `eth_getLogs`, never sends the portal's key to the RPC, and a fallback carried with nothing left reads nothing from either source; a lane whose windows charge three times what they send pays the charge and reports the sends; a shared walk from the portal writes the rows of the two RPC walks; and the pinned request traces are unchanged in `rpc` and `shadow` modes.
