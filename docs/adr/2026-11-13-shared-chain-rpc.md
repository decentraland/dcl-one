# ADR: Shared Ethereum RPC readers

- Status: Accepted
- Date: 2026-11-13

## Decision

The existing `catalyst-chain-index` crate owns Ethereum JSON-RPC log and header transport in its `rpc` module. LAND authorization and Shop consume that module directly. The client holds the outbound transport and endpoint; callers supply address and topic filters. It does not hold LAND registry settings.

The shared module owns response parsing, bounded log-range retries, header batches and generic transport, RPC and request-budget errors. LAND authorization retains registry filters, timestamp validity and batch retry policy, request accounting, cursor advancement, fold readiness and repair. Its error conversion retains domain error distinctions and messages. Shop retains receipt checks, index folds, reorganization handling and Credits settlement policy.

This keeps shared chain-reading mechanisms below domain policy without another crate, outbound client, pool or deployment. Existing layer dependencies already permit both consumers to use chain-index. No schema, HTTP route, authorization rule or request budget changes.

The Shop chain walk reads through the `logs` module's `LogSource`. A source answers the chain id it serves, the newest block, the newest finalized header, a header by height, a window of logs for a set of filter groups with the block it proved complete, and the block times of those logs. Each read reports the requests it took, as the walk charges them to its budget: for JSON-RPC, HTTP requests, a batch counting one. That count is not a provider's bill and is not comparable across sources as is. `RpcSource` is the JSON-RPC implementation: one request per chain id, head, finalized or header read, and the window and block-time reads described above, including halving the address chunk when the endpoint refuses the count. The walk keeps the target block, confirmation depth, cursor, request budget, cancellation, reorganization handling and publication, and its backfill lanes read through the same source.

A portal that speaks the SQD portal protocol (the SQD portal, or chain-lake's) is read by the `portal` module's `PortalReader`, which is not a `LogSource`: no walk reads from it. It reads finalized blocks only (`/finalized-stream`), the dataset's latest and finalized heads, and the dataset's advertised first block where the portal publishes metadata. A page counts only when its body is complete and decoded and ends with the last block it covered; an empty answer, a cut body or a 204 covers nothing. The reader sends its key as `x-api-key` to the configured origin only, follows no redirect, and shares one rate limiter and cooldown per origin and key in the process. A portal's answer proves which blocks it covered, not that it holds every log of the addresses asked: the advertised first block bounds the dataset only, and address history is unknown unless the operator asserts it (`CHAIN_LOGS_PORTAL_ASSERT_FULL_HISTORY`), which is reported as an assertion.

With `CHAIN_LOGS_SOURCE=shadow` and `CHAIN_LOGS_PORTAL_URL`, each network runs a shadow worker. A walk alone and a shared walk call `LogSource::accepted` once a window's bracket and predecessor check pass, before its commit; the shadow takes the read only when its one slot is free and the read is within the hand-off bounds, otherwise it counts the skip, so the walk never waits and reads nothing more. The worker reads the same filters over the same blocks from the portal, with up to two drain rounds, within one 20-second deadline. It compares only a prefix anchored at the highest block where both sides hold a hash, and equal hashes there let that prefix be compared log by log; different hashes are a branch mismatch. A field one side lacks (a log's block hash, its time, its transaction hash) is not compared, and a read with such a field is incomplete, never equal. Only the dataset's advertised first block is cached (ten minutes); every comparable sample is anchored on its own. Backfill lanes are not compared. Outcomes are counted in `chain_logs_shadow_windows_total{net, result}`, `chain_logs_shadow_skipped_total{net, reason}`, `chain_logs_shadow_logs_total{net, kind}`, `chain_logs_shadow_unavailable_total{net, field}`, `chain_logs_shadow_blocks_total{net, kind}` and `chain_logs_portal_sends_total{net, kind}`. `CHAIN_LOGS_PORTAL_DATASET_{ETHEREUM,MATIC}` name the datasets (mainnet by default), `CHAIN_LOGS_PORTAL_API_KEY` (or its `_FILE`) the key, and `CHAIN_LOGS_PORTAL_MAX_RPS` (1) the rate. The walks commit RPC data in either mode.

`catalyst shop compare-sources` compares one index over a block range: a read-only database connection for its filters, the walk's bracket on the RPC side, and the same filters on the portal. The network, the dataset and the RPC must name one chain before any window is read, or the run is refused. It reports the compared ranges, the uncovered ones with their reason (below the dataset's first block, above the RPC's safe head or the portal's finalized head, a window it could not anchor, or a read that failed, which ends the run with what was compared so far), the differences, the logs each side held in what it compared (the portal's as the exact filter keeps them, so an equal verdict over no logs reads as such), the fields it could not compare, and the requests each side took. Every outcome prints its report: an unreachable database is reported before any chain read, and a failure by its stage, blocks and a stable kind, never by an upstream's text. It exits 4 when refused, else 1 when anything differed, else 3 when part of the range or a compared field was not compared, else 0; without a report, 2 is the argument parser's usage error and 1 a process setup error before the command runs (an invalid `NODE_POSTURE`); a difference always prints its report. The database's cursor of the index must be bound to the network's chain when it is bound at all (`database_chain` reports it).

## Validation

The chain reader parser tests run in chain-index. LAND integration tests exercise range hints, budget exhaustion, missing timestamps, batch fallback and retry, replay and publication. Shop tests exercise its filters, reorganization boundaries and Credits index consumers. A Shop integration test pins the order of the JSON-RPC requests the walk sends for one history, with each log request's block range and address count and each batch's headers: budgeted passes, an address-count refusal, missing timestamps, a pass with nothing new, a backfill lane and a reorganization rewind. The module dependency check enforces the existing layer graph. The portal client's tests run against a loopback portal: early ends, 204, cut bodies, size rejections, redirects and the key's header. The comparison tests cover the anchor, branch mismatches, conflicts and filter arity; the shadow tests cover the hand-off's bounds and a stalled portal; the pinned request traces are unchanged with a stalled shadow; and `compare-sources` runs over a fake chain and a fake portal serving it.
