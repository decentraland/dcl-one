# Repository-wide gateway and sync coverage

**Decision:** keep the current bounded pilot. Add service coverage by operation, with native replay first and production → dcl-one outcome sync only where replay cannot reproduce the required facts. The repository sweep identifies additional scope and ownership questions; it does not establish that these services are ready for public target traffic.

## Scope and confidence

Checked on 2026-11-12: **246 top-level Git checkouts inventoried; 73 selected service/support repositories refreshed from their remote default branches.** One additional refresh attempt (`rewards`) has no origin. Default branches include `master` and `biz`; existing working branches and local edits were preserved. Duplicate clones are not independent services. Hidden worktrees, dependencies and scratch directories are not additional source repositories.

The [complete repository catalog](repository-inventory.md) records every checkout, its evidence revision and disposition. Service entrypoints, writers and storage were reviewed by group; other checkouts received file-layout screening. This is not an exhaustive line-by-line audit, a live deployment inventory or proof that every target endpoint is compatible. Earlier detailed audits retain their own revision pins.

## In-scope priorities

The repository inventory is broader than dcl-one's migration scope. **Discovery is not a separate migration source: its product functionality is Places and Events in dcl-one. CMS and warehouse feeds are not dcl-one services; Exploration Games is out of scope.** Their existence in the checkout inventory does not create a gateway or synchronization requirement. Mobile BFF is not automatically included either; target scope must be established before proposing work.

The next relevant coverage is **worlds-content-server and world-storage-service**, both represented in dcl-one and in the initial migration. Their [focused replay/sync assessment](worlds-creator-sync-audit.md#worlds-recheck-and-next-contracts) separates request replay, derived state and source-job outcomes. Bounded player-command replay and owner/quota capture are implemented; see the [exact boundary](worlds-background-contract.md#implemented-boundary).

## Service disposition

“Retain” means keep the dependency source-owned, not ignore it during activation. Gateway candidates still need signed URL/body compatibility, authentication, response and transport budgets, durable acceptance, ordering and effect suppression. Jobs and internal calls are not automatically residual writers: first assess whether their accepted inputs can join native replay.

## Implementation order and activation gates

1. **Finish the existing Places pilot rehearsal and Events command contract.** Keep unclassified writes blocked; no new whole-service capture adapter follows from the repository inventory.
2. **Define World Storage native replay:** world/player setters, deletes and clears, then env operations. Preserve accepted scene/place identity, authentication, order and source-owned limits. Prove target namespace compatibility before enabling routing.
3. **Define Worlds content commands:** permissions and settings, then deployment/undeployment with verified immutable bytes. Keep live revocation, providers and queue publication production-owned.
4. **Assess exact Worlds job outcomes:** owner changes, quota block creation/removal and eviction. Compare captured input replay with minimal committed-outcome mapping; never run independent external-data decisions in both instances.
5. **Verify deployed ingress and internal writers for these in-scope services.** Scene/runtime calls must reach the chosen gateway or durable acceptance path. Rehearse ordering across deployments and storage writes, deletion, retries and recovery before activation.

No additional gateway route or sync adapter was enabled by this audit. Favorites/votes remain native replay; residual projections remain limited to POI membership and scoped Worlds owner/quota facts. Shop, treasury, credits and marketplace stay excluded for security reasons. Voice, notifications, rewards, push, uploads and scene sessions retain one effect owner until a separate handover is proven.
