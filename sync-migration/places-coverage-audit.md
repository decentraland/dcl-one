# Places coverage audit

Reviewed 2026-11-12 against Places `ba6674f6f13c2715be3e480d4b01b6979cde79fc` and the local dcl-one sync implementation. This is a source-code inventory, not confirmation of deployed schema, task configuration, external scripts or traffic.

## Decision

Rehearse the existing Genesis UUID allowlist first. Capture committed catalogue and interaction results while production retains every consumer, scheduler and provider effect. Complete public read compatibility and scope expansion before calling this a Places service migration. No source HTTP-handler or client PR is required for this source-only strategy; installation of capture SQL and reviewed grants is required.

## Concrete compatibility defect found and corrected

The adapter initially compared its UUID scope keys directly with source character IDs. Places explicitly documents `places.id` as `character(36)` in [its model](https://github.com/decentraland/places/blob/ba6674f6f13c2715be3e480d4b01b6979cde79fc/src/entities/Place/model.ts#L39); the original migrations use the Gatsby `Type.UUID` shorthand, which resolves to `CHAR(36)`. Interaction columns use the same initial shorthand; the [entity rename migration](https://github.com/decentraland/places/blob/ba6674f6f13c2715be3e480d4b01b6979cde79fc/src/migrations/1770729788000_rename-place-id-to-entity-id.ts) renames them without changing their type. World-name interactions are therefore possible without PostgreSQL UUID-typed columns.

Direct UUID/character equality can fail during installation, bootstrap, catalogue writes or reconciliation. UUID-only test fixtures hid this incompatibility. The fix compares textual representations in source queries/triggers, keeps scope validation canonical, and never casts arbitrary source world IDs to UUID. The optional favorite command path receives the same correction. Target schema and wire IDs are unchanged.

The [capture regression](../services/migration-sync/tests/capture.rs) now starts with character IDs and unscoped world-name facts, exercises bootstrap, updates, deletes, reconciliation and optional command receipts. It also rejects an uppercase scoped interaction ID during bootstrap without registering a target stream. A separate run with `varchar(255)` interaction fixture columns also passed; that is compatibility coverage, **not a claim about the deployed source schema**. Changing source column types while capture is active is not supported. Scope lookup is case-insensitive so noncanonical scoped IDs reach validation and fail closed rather than silently disappearing from the baseline. See [implementation evidence](implementation.md) for final validation status.

## Prioritized next work

1. **Before rehearsal:** apply the character-ID fix, verify actual source column types and grants, enumerate every source writer, and use a fixed scope with replacement-ID monitoring. Reject any claim that finite scope covers all future deployments.
2. **First rehearsal:** run a real POI category job, ranking batch and Genesis deployment replacement against disposable production-shaped fixtures; compare committed scoped outcomes and measure lock overhead, transaction sizes and lag. Existing tests of POI SQL alone do not prove scheduler integration.
3. **Before public reads:** compare discovery, ranking, parcel lookup, categories and interaction response shapes. Live cache values and authorization need their own source of truth. Validate catalogue removal intents remain inert.
4. **Before longer coexistence:** design explicit admission of newly created UUIDs and a consistent baseline for newly admitted keys. The current immutable-scope contract intentionally has no automatic expansion. Implementing this belongs in dcl-one capture/control; it does not inherently require client modifications.
5. **Only with explicit requirements:** add normalized category registry/history and moderation history mappings; then assess worlds as a dependency-complete scope. Preserve a single ingestion/effect owner throughout.

## Source PR rationale

The required change is a source-local outbox installation: it captures committed SQL changes from APIs, jobs and internal writers that gateway duplication cannot see. Keep its installation, grants, stop/removal procedure and staging evidence reviewable alongside the dcl-one adapter. A Places application PR is needed only if that repository owns deployment migrations, or if the optional native-command receipt protocol is deliberately enabled. Neither reason authorizes changing normal Places handlers for the current source-only rehearsal. No gateway/client PR is required for copying these facts.
