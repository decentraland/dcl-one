# Remaining services: sync feasibility and missing dependencies

Reviewed 2026-11-12 from local source revisions pinned in the links below. This is static code and mapping evidence, not a deployed-version, role, traffic or cloud-schedule inventory. No new continuous mappings or production installations are implemented by this audit.

**Decision:** reproduce compatible operations in both backends first. Classify queue consumers, scheduled jobs, provider webhooks, Redis state and configuration changes individually: bypassing the gateway does not prove an operation cannot be replayed. Use production → dcl-one DB sync only for demonstrated residual outcomes, with provenance that prevents applying native results twice. Keep production as the sole external-effect owner; the [operation matrix](operation-classification.md) defines the acceptance requirements.

## Inventory boundary

The [batch source catalog](../tooling/migration/sources) contains 16 sources: badges, builder-server, camera-reel-service, comms-gatekeeper, credits-server, events, marketplace-favorites-server, marketplace-server, notifications-workers, places, referral-server, shop-server, signatures-server, social-service-ea, world-storage-service and worlds-content-server. The retained pilot executes accepted favorite/vote commands and maps only the justified POI membership outcome; broader source-only adapters remain removed. A batch mapping is not a continuous delete/order/recovery contract.

Shop, credits, treasury and both marketplace sources remain excluded for security reasons. Signatures/rentals are deferred because their target status depends on excluded shop chain data. Source names outside this catalog must be classified as deliberately retained dependencies or missing migration scope; absence is not evidence they are stateless.

## Concrete reliability finding

The reviewed Notifications [message processor](https://github.com/decentraland/notifications-workers/blob/d1cb1215de04a1dffe250de441f160685d8fb76b/processor/src/adapters/message-processor.ts#L41) deletes the queue message in `finally` even when `saveNotifications` throws. A database failure can therefore acknowledge an event without a committed notification. CDC can reproduce committed facts only; neither it nor the gateway can recover that missing event from the DB.

A focused Notifications source PR should change acknowledgement/retry handling and test failed database writes, poison-message policy and redelivery. This needs delivery semantics too: [email sending](https://github.com/decentraland/notifications-workers/blob/d1cb1215de04a1dffe250de441f160685d8fb76b/processor/src/adapters/notifications-service.ts#L99) is deferred with `setImmediate` after insertion and has no durable completion receipt in this path. An acknowledged row is not proof that mail was sent; merely retrying inserts does not establish mail delivery. These are code findings, not a reproduced production incident. No source fix is implemented here.

## Gateway and implementation consequences

1. **Enable only classified operations.** Proven mutations use durable duplicate execution after production acceptance; public target reads require separate compatibility and freshness checks. Auth/login, notification-read mutations, moderation, stream credential issuance and voice cannot be enabled through broad service-level shadow rules. GET/upgrade semantics and internal callback paths need endpoint review, not a method-only assumption.
2. **Keep one source owner per dataset and effect.** Queue/webhook/job sources need explicit replay assessment, residual capture or handover even if all public clients use the gateway. Do not attach another competing consumer to production queues to simulate replication.
3. **Classify Notifications and Badges by operation.** Read receipts/subscriptions/catalog administration are duplicate candidates; queue/evaluator outcomes are residual candidates with explicit deletes, identity and no-delivery guarantees. Moderation follows resolved catalogue identities; authorization enforcement needs a stricter freshness contract than public counts.
4. **Expand source PRs only for demonstrated needs.** Compatible commands need acceptance/identity/retry evidence, possibly a source receipt path. Only a justified residual projection needs its own exact capture and transformation; neither requires adding sync calls indiscriminately to every HTTP handler. The Notifications acknowledgement defect needs a separate source fix; provider handover or durable delivery receipts may need application changes. Auth/config replacement remains a scope decision, not an automatic migration requirement.
5. **Before claiming service completeness**, inventory deployed queue subscriptions, webhook destinations, cron jobs, external scripts, Redis keys, object assets, feature configuration and secret owners. This review establishes their code paths, not their deployed configuration or load.
