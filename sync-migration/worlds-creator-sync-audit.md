# Worlds, creator data and content: sync feasibility

Reviewed 2026-11-12 against local source revisions listed below. This is a targeted code and mapping audit, not deployed-schema verification or full endpoint conformance. **Bounded player-command replay and Worlds owner/quota capture are now implemented; other operations below remain unimplemented.** Their batch importers are useful transformation references, not a substitute for capture.

## Decision

Follow the [decision summary](README.md): assess compatible native replay before adding residual DB sync. Generated IDs, uploads, publication messages and permission callbacks are compatibility questions to resolve, not automatic grounds for copying whole tables. Keep one production effect owner.

The table below inventories dependencies any chosen lane must satisfy. No Camera, Builder or broad Worlds DB adapter is approved by this audit. Owner/quota/eviction outcomes are residual candidates if replaying their inputs cannot safely reproduce them. Reuse existing content peer replication where compatible, with separately isolated ingestion.

## Jobs, callbacks and bytes the gateway cannot reproduce

- **World owners and quota:** the [12-hour owner job](https://github.com/decentraland/worlds-content-server/blob/10af5255bb04a1a28e0c26bd190317c26a6015a9/src/adapters/update-owner-job.ts) changes ownership and refreshes/removes quota blocks using external ownership resolution. The [daily eviction job](https://github.com/decentraland/worlds-content-server/blob/10af5255bb04a1a28e0c26bd190317c26a6015a9/src/adapters/eviction-job.ts) removes old undeployed scenes. Assess deterministic replay first; otherwise these resulting facts are residual candidates. Do not run independent target decisions during coexistence.
- **Uploads and GC:** [partial-upload cleanup](https://github.com/decentraland/worlds-content-server/blob/10af5255bb04a1a28e0c26bd190317c26a6015a9/src/adapters/partial-upload-cleanup-job/component.ts) runs at start and periodically. Pending uploads are not portable completed scenes. Keep them on their original owner, drain or explicitly cancel them at cutover. Target GC must not delete newly copied bytes before their references are committed; source deletion can also race a delayed copy, so define retention/retry semantics.
- **Permission effects:** [Social member-removal callbacks](https://github.com/decentraland/worlds-content-server/blob/10af5255bb04a1a28e0c26bd190317c26a6015a9/src/controllers/handlers/community-member-removed-handler.ts) can kick participants. Target [revocation callbacks](../services/catalyst/worlds/src/core/mod.rs) are not invoked by copying SQL rows. Keep live admission/media on production until stale authorization and eviction are addressed explicitly.
- **Photo events:** Camera SNS publication occurs after the metadata commit and failures are logged without rolling back the photo. Captured rows prove the photo exists, not that Social received its ranking event. Do not republish from dcl-one and risk double effects; repair delivery separately if required.
- **Secrets and configuration:** world-storage encrypted values require the compatible encryption key/layout, handled through deployment secrets rather than documents or gateway payload logs. Worlds blocked names and per-world whitelist limits live outside the DB; the batch importer already requires explicit policy checks. Redis rate-limit state is not business-data replication and needs an explicit enforcement owner.

## Concrete incremental-import finding

The reviewed owner job executes `UPDATE worlds SET owner = ...` without changing `updated_at`; reviewed source migrations do not define an automatic timestamp-update trigger. dcl-one's [world step](../tooling/migration/sources/worlds-content-server/source.toml) selects `updated_at` as its watermark. Consequently `--since last` can miss an ownership transfer once the unchanged timestamp falls outside the overlap window. This is a static code finding, not a reproduced production incident.

A full world rescan or transaction capture observes the row change. A source fix could update the timestamp and add a regression test, but that alone would not solve deletes, late commits or cross-table snapshot consistency. Do not advertise periodic incremental batch runs as a complete sync mechanism. This audit does not modify that importer or source job.

## Operation classification and source PR rationale

Follow the [operation backlog](operation-classification.md). Camera/Builder mutations, world permission/storage edits and deployments must first be assessed for compatible replay with identical IDs, bytes and effect suppression. Owner/quota/eviction outcomes are residual candidates when source computation cannot safely be reproduced. Do not turn a service inventory into a table-wide sync implementation.

Any residual world/storage mapping needs coordinated identities, blob retention, namespace provenance and deletion/winner recomputation. Any replay path needs durable source acceptance and target receipts. Source application PRs are justified by these explicit contracts or concrete defects, such as the owner timestamp issue, not by the presence of a database.

Content/profile peer synchronization is a separate existing protocol to validate with isolated ingestion. Public routing remains blocked until required facts, authorization and bytes are complete. The bounded implementation and required source changes are recorded in the [background contract](worlds-background-contract.md#implemented-boundary); no deployment or production load/reconciliation test has been performed. Actual source schemas, custom writers, queue subscriptions, object retention and ingress remain unverified.
